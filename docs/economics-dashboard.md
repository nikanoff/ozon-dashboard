# Дашборд как финансовый инструмент: анализ и проект

Аудит: 2026-10-03. Основа — действующий проект `ozon-dashboard` и официальный Seller API
(`docs.ozon.ru/api/seller/swagger.json`, 463 операции).

Три вопроса, на которые отвечает документ:

1. **Что доступно бесплатно** — и почему README проекта в этом ошибается.
2. **Что должен показывать дашборд**, если смотреть на магазин как экономист, а не как
   на таблицу заказов.
3. **Как это встроить** в существующий проект, не переписывая рабочую часть.

---

## 0. Главное в одном абзаце

Действующий дашборд показывает **выручку**, а продавец зарабатывает **не выручку**.
По данным практика, на Ozon до счёта доходит 79,8 % от того, что заплатили покупатели,
и разброс по товарам — от 40 % до 70 %. То есть текущий дашборд системно завышает
представление о бизнесе **в 1,25–2,5 раза**, причём неравномерно по ассортименту: выводы
о «хороших» и «плохих» товарах, сделанные по выручке, могут быть прямо противоположны
выводам по деньгам. Хорошая новость: почти всё, что нужно для денежной картины, лежит
в **бесплатных** методах, а один из источников проект **уже запрашивает и выбрасывает**.

## 1. Что доступно на бесплатной подписке

### 1.1 Группировка методов

Официальный swagger делит 463 операции на 4 группы, и это де-факто карта подписок:

| Группа | Методов | Доступ |
| --- | ---: | --- |
| Базовые методы | 312 | бесплатно |
| Бета-методы | 126 | бесплатно, но форма ответа может меняться без предупреждения |
| Ozon Доставка | 15 | другая интеграция (внешние магазины), не про маркетплейс |
| **Premium-методы** | **10** | **требуют подписки Premium** |

Полный список Premium-методов (всего десять):

```
POST /v1/analytics/data                    — Данные аналитики
POST /v1/analytics/product-queries         — Запросы моих товаров
POST /v1/analytics/product-queries/details — Детализация запросов по товару
POST /v1/search-queries/text               — Поисковые запросы по тексту
POST /v1/search-queries/top                — Популярные поисковые запросы
POST /v1/finance/realization/by-day        — Реализация за день
POST /v1/product/prices/details            — Подробная информация о ценах
POST /v1/chat/send/message                 — Отправить сообщение
POST /v1/chat/start                        — Создать чат
POST /v2/chat/read                         — Отметить прочитанным
```

Отдельный случай: `ReviewAPI` (отзывы, 12 методов) лежит в бета-группе, но требует
подписки «Управление отзывами» или Premium Pro — гейт не по группе, а по описанию метода.
**Отсюда правило: доступность метода определяется его описанием, а не группой.**

### 1.2 Что это значит для README проекта

README утверждает:

> Финансы, аналитика и отзывы требуют платной подписки Ozon и на бесплатном тарифе
> недоступны, поэтому в дашборд не встроены.

Это неверно для двух пунктов из трёх:

- **Финансы доступны.** `FinanceAPI` (10 методов) и `ReportAPI` (11 методов) целиком в
  базовой группе. Отчёты о реализации, о компенсациях, о выкупленных товарах, о
  размещении — всё бесплатно. Платный только `realization/by-day`.
- **Аналитика доступна частично.** Бесплатны `/v1/analytics/stocks`,
  `/v1/analytics/turnover/stocks` (оборачиваемость!), `/v2/analytics/stock_on_warehouses`.
  Платные — только `analytics/data` и запросы/поисковые запросы.
- **Отзывы — да, платные.** Здесь README прав.

То есть проект недооценил бесплатный тариф и не построил финансовый слой там, где он был
возможен с самого начала.

## 2. Критично: финансовый API сменился, пока проект стоял

Это самый важный технический факт документа, и он датирован.

**8 сентября 2026 года Ozon отключил `/v3/finance/transaction/list` и
`/v3/finance/transaction/totals`.** Анонс был 6 мая с датой 6 июля, но 6 июля метод
продолжал работать, в августе не был помечен как deprecated, а 8 сентября начал отвечать:

```
HTTP 400 {"code": 9, "message": "obsolete method cannot be used"}
```

Сегодня 2026-10-03 — то есть отключение произошло **90 дней назад**. Любой новый код,
написанный по старой документации, будет молча получать ошибки (или, что хуже, пустой
результат, который легко принять за «начислений ещё нет»).

### 2.1 Чем заменять

Замена — **`/v1/finance/accrual/by-day`** (бета-группа, бесплатно). Интерфейс отличается
не версией, а устройством:

| Свойство | Старый `transaction/list` | Новый `accrual/by-day` |
| --- | --- | --- |
| Период | произвольный диапазон | **строго один день**: `{"date": "2026-09-15"}` |
| Ошибка на период | — | `value length must be 10 runes` |
| Пагинация | `page` / `page_size` | **курсор** `last_id` в ответе; пустая строка — конец |
| Структура | плоский объект | вложенная, с `accrued_category` |
| Категории | нет | `POSTING` (по отправлению), `ITEM` (по товару, включая эквайринг), `NON_ITEM` (прочее) |

Соответствие полей (подтверждено практиком на данных, а не по документации):

```
accrual_id          -> operation_id
date                -> operation_date
unit_number         -> posting_number
total_amount.amount -> amount
```

**`accrual_id` равен прежнему `operation_id`** — значит upsert остаётся идемпотентным,
историю не нужно переписывать, старые и новые данные стыкуются без шва.

Для `by-day` поле `total_amount` **уже нетто**: цена продавца минус комиссия минус
логистика, и `ITEM`-начисления приходят тем же потоком.

### 2.2 Яма на 1,2 %, в которую легко попасть

Рядом лежит `/v1/finance/accrual/postings` — лукап по номерам отправлений, до 200 за
запрос. Выглядит идеально: не надо обходить дни. **Для чистого дохода не годится:**
он отдаёт только `POSTING`-начисления, а приём платежа (эквайринг) лежит в категории
`ITEM` и в этот метод не попадает. Сумма по заказу выходит меньше примерно на **1,2 %** —
достаточно мало, чтобы не заметить, и достаточно много, чтобы не сходиться с кабинетом.
Плюс выручка там в отдельном поле `seller_price`, а не в `total_amount`.

Для «этот заказ в плюс или в минус» нужен только `by-day`.

### 2.3 Ещё три грабли

- **`amount` — источник истины, не пересчитывайте его.** У штрафов, страхования и
  компенсаций нет ни начислений, ни услуг — только `amount`. На выборке 400 операций так
  расходятся 35. Сложение `accruals_for_sale + sale_commission + services` даёт неверный итог.
- **Услуги разбросаны и не названы.** У отправления — `posting.products[].delivery.services`;
  у товара — `item_fees.fees[].fees[]` (два уровня `fees`); у прочего — `non_item_fee` и
  `container_fees`. Названий нет, только `type_id`; расшифровка — справочник
  `/v1/finance/accrual/types` (статичный, кешируется один раз).
  Практик советует **рекурсивный обход дерева** вместо жёсткой схемы: пять строк, которые
  переживут следующую смену формы ответа.
- **Операции без `posting_number` — расходы кабинета**: хранение, реклама, сбор отзывов.
  Их **нельзя размазывать по заказам**: цифра по отправлению должна совпадать с кабинетом,
  иначе в споре с площадкой продавец проиграет собственной таблице. Это отдельная строка P&L.

## 3. Экономическая модель магазина

### 3.1 Три уровня правды о деньгах

| Уровень | Источник | Что даёт | Для управления |
| --- | --- | --- | --- |
| 1. Заказы | `/v3/posting/fbo/list` | цена товара — **деньги покупателя**, не ваши | не годится |
| 2. Отчёт о реализации | `/v2/finance/realization` | одна сумма за месяц, через ~2 недели после периода | для бухгалтерии |
| 3. Финансовые операции | `/v1/finance/accrual/by-day` | каждое начисление и удержание с привязкой к отправлению | **только здесь** |

Текущий дашборд живёт на уровне 1 и называет это «Net Sales». Экономически это GMV
продавца, а не выручка.

### 3.2 Мост P&L (что должно быть на экране)

```
Начислено за товар (seller_price)              +100 000
  Комиссия площадки                             −48 000
  Логистика                                      −3 000
  Обработка отправления                            −300
  Последняя миля                                   −340
────────────────────────────────────────────────────────
NET PAYOUT (то, что дойдёт до счёта)            48 360   (48,3 %)
  Приём платежа (ITEM, эквайринг)                −???     ← отдельным потоком
  Себестоимость товара (COGS)                    −???     ← нет в API
────────────────────────────────────────────────────────
Валовая прибыль                                     ???
  Расходы кабинета: хранение, реклама, отзывы    −???
────────────────────────────────────────────────────────
Прибыль кабинета                                    ???
```

Цифры этого заказа — из разбора практика (реальный кабинет, обычная категория,
покупатель забрал с первого раза): продавцу остаётся меньше половины цены заказа.

Эквайринг в этот пример не входит: он лежит в отдельной категории `ITEM` и в разобранном
заказе не показан. Во втором примере практика он есть и составляет около 1 % суммы: без
него расчёт вышел бы больше правильного на эту же величину. Порядок величины — около 1 %, —
именно из-за него `accrual/postings` и не годится для расчёта чистого дохода.

Два вывода, которые определяют весь дизайн:

1. **`payout ratio` (net / GMV) — главный операционный KPI продавца.** Он не константа:
   по кабинету практика 79,8 % в целом и от 40 % до 70 % по отдельным товарам. Разброс —
   это и есть управленческая информация: где чинить цену, а где выходить из товара.
2. **COGS в API нет и не будет.** Себестоимость знает только продавец. Без неё «маржа» —
   фикция, поэтому ввод себестоимости — не «дополнительная фича», а условие существования
   финансового дашборда. Пока COGS не задан, интерфейс обязан честно показывать
   «маржа без себестоимости», а не рисовать прибыль.

### 3.3 Что измерять: пять блоков

**A. Деньги (P&L)**

| Показатель | Формула | Источник |
| --- | --- | --- |
| GMV продавца | Σ `seller_price` × шт | accrual / posting |
| Удержания Ozon | Σ комиссия, логистика, обработка, последняя миля, эквайринг | accrual + `financial_data` |
| **Net payout** | Σ `total_amount` | accrual/by-day |
| **Payout ratio** | net / GMV | расчёт |
| Расходы кабинета | Σ `NON_ITEM` без `posting_number` | accrual |
| Компенсации и штрафы | по `type_id` | accrual/types |
| COGS | Σ себестоимость × шт | **ввод продавца** |
| Валовая прибыль, маржа % | payout − COGS | расчёт |
| Маржа на единицу / на заказ | — | расчёт |
| Минимальная цена по SKU | `(COGS + удержания) / (1 − комиссия%)` | расчёт |

**B. Капитал (оборотный)**

| Показатель | Формула | Источник |
| --- | --- | --- |
| Запас в закупке | Σ остаток × COGS | stocks + COGS |
| Запас в ценах продажи | Σ остаток × цена | stocks + prices |
| Задолженность Ozon | сальдо | `/v1/finance/balance` (β) |
| Деньги в пути | начисления по delivered, но не выплаченные | accrual |
| **Замороженный капитал** | Σ COGS по `dead` + `overstock` | inventory + COGS |
| Стоимость хранения | Σ `NON_ITEM` type=storage | accrual/types |
| Cash conversion cycle | закупка → поставка → продажа → выплата | по датам |

**C. Эффективность**

| Показатель | Формула | Источник |
| --- | --- | --- |
| Оборачиваемость (IC) | COGS за период / средний запас | расчёт |
| Дни запаса | остаток / среднесуточный спрос | `ads`, `idc` из turnover |
| **GMROI** | валовая прибыль / средний запас в закупке | расчёт |
| Sell-through | продано / (продано + остаток) | расчёт |
| **Упущенные продажи** | Σ дефицит × `demandPerDay` × дни × цена | stocks + postings |
| **Упущенная маржа** | то же × маржа на единицу | + COGS |
| ABC по марже | кумулятивная доля маржи | расчёт |
| XYZ по стабильности | коэффициент вариации спроса | расчёт |

Обратите внимание: ABC сейчас в проекте считается **по выручке**
(`revenueConcentration`). Для управления ассортиментом это неверно: товар может давать
30 % выручки и 5 % маржи. Экономисту нужен ABC **по марже**.

**D. Риск**

| Показатель | Источник |
| --- | --- |
| Доля отмен | postings (есть) |
| Доля возвратов и невыкупов | `/v1/returns/list`, `/v2/report/returns/create` |
| **Доля выкупа** | delivered / (delivered + возвраты + невыкупы) |
| Стоимость обратной логистики | accrual (в новом API возврат приходит обычной услугой) |
| Рейтинг продавца | `/v1/rating/summary` |
| Индекс цен | `rating_price_index`, `color_index` |
| Ошибки ОВХ (габариты) | `/v1/product/info/wrong-volume` → переплата логистики |
| Концентрация маржи | доля топ-1 / топ-3 SKU в марже |
| SKU с отрицательной маржой | расчёт |

**E. Сейчас (операционный пульт)**

- заказы за сегодня и темп к вчера;
- воронка статусов и **просроченное** (`awaiting_packaging` с дедлайном);
- дефицит на бестселлерах прямо сейчас;
- **лента «Требует действия»**: ранжированный список с причиной и суммой эффекта.

## 4. Проект дашборда

Принцип: верхний экран отвечает на вопрос «в каком состоянии магазин и что делать», а не
показывает исторические графики. Аналитика — ниже, по требованию.

### Экран 0 — «Пульс» (главный, всё выше сгиба)

Четыре плитки и одна лента.

```
┌─ ДЕНЬГИ ────────────────────┐ ┌─ КАПИТАЛ ─────────────────┐
│ К перечислению    100 000 ₽ │ │ Запас в закупке    200 000│
│ Payout ratio        72,4 %  │ │ Должен Ozon         50 000│
│ Удержания Ozon     25 000 ₽ │ │ Заморожено          75 000│
│ Δ к пред. периоду    +6,1 % │ │ Хранение за мес.     8 400│
└─────────────────────────────┘ └───────────────────────────┘
┌─ ЭФФЕКТИВНОСТЬ ─────────────┐ ┌─ РИСК ────────────────────┐
│ Оборачиваемость     3,1 ×   │ │ Доля отмен          2,4 % │
│ GMROI              148 %    │ │ Доля выкупа        91,2 % │
│ Дней запаса (медиана)  42   │ │ Рейтинг            4,82   │
│ Упущено маржи      23 100 ₽ │ │ SKU в минусе           7  │
└─────────────────────────────┘ └───────────────────────────┘

ТРЕБУЕТ ДЕЙСТВИЯ
● 4 бестселлера кончатся за ≤5 дней — упустите ~18 400 ₽ маржи
● 7 SKU продаются ниже себестоимости — минус 6 200 ₽ за месяц
● Хранение неликвида: 12 SKU, 41 000 ₽ заморожено, 2 100 ₽/мес
● 3 товара с красным индексом цен — теряете показы
● 12 отправлений ждут упаковки, 2 просрочены
```

На графике — **net payout по дням**, не выручка, и рядом линия payout ratio.

### Экран 1 — Юнит-экономика

- Мост P&L (waterfall) за период: GMV → комиссия → логистика → эквайринг → возвраты →
  прочее → **payout** → COGS → прибыль.
- Таблица SKU: цена, фактическая комиссия %, payout на единицу, COGS, маржа ₽ и %,
  оборот, GMROI, дни запаса, вердикт (масштабировать / поднять цену / вывести).
- Товары с отрицательной маржой и расчёт минимальной цены для них.
- Глубина скидок: `old_price` против `price` и какие `actions` её дали.
- Фактическая комиссия против номинальной по категории — где Ozon берёт больше, чем вы думали.

### Экран 2 — Оборотный капитал

- Матрица ABC (по марже) × XYZ (по стабильности): где деньги и как быстро возвращаются.
- Замороженный капитал: неликвид и избыток в рублях закупки, а не в штуках.
- Упущенные продажи и упущенная маржа по SKU.
- Стоимость хранения по товарам — прямые потери от избытка.
- Cash conversion cycle и «деньги в пути».

### Экран 3 — Риск и качество

Возвраты и невыкупы по товарам, стоимость обратной логистики, доля выкупа, рейтинг
продавца и его составляющие, индекс цен, ошибки ОВХ, концентрация маржи.

### Экран 4 — Действия

- **Replenishment**: «закажи N шт, чтобы закрыть X дней» по каждому дефицитному SKU, с
  учётом срока поставки.
- Очередь операционных задач (упаковка/отгрузка с дедлайнами).
- Кандидаты на выход из ассортимента с суммой высвобождаемого капитала.

## 5. Что делать с текущим проектом

### 5.0 Состояние реализации

Этапы A–E внедрены. Ниже — что именно появилось в коде, чтобы план не расходился
с действительностью.

| Этап | Модули | Что даёт на экране |
| --- | --- | --- |
| A | `lib/economics.ts`, правки `ozon_types.ts` и `ozon_map.ts` | Раздел «Деньги»: комиссия и её фактическая ставка, остаток продавцу, отдано скидками; в таблице заказов «цена → продавцу» по строке |
| B | `lib/costs.ts`, `stores/cogs.ts`, `components/CogsPanel.svelte` | Книга себестоимости с датами, импортом и выгрузкой. Раздел «Маржа и ассортимент» (валовая прибыль, маржа, ABC по прибыли, убыточные SKU) **удалён по просьбе продавца**: себестоимость теперь нужна карточкам и цепочке «от реализации до счёта», а кнопка ввода переехала в заголовок раздела «Деньги» |

### 5.1 Бесплатный обед: вернуть выбрасываемые поля

Проект **уже** запрашивает финансовые данные:

```ts
// src/lib/server/ozon.ts:212
with: { analytics_data: true, financial_data: true }
```

и **выбрасывает почти всё** в `toDashboardPosting`: из `financial_data` остаются только
`cluster_from`, `cluster_to` и `actions`. При этом `financial_data.products[]` содержит:

```
commission_amount      — комиссия в рублях
commission_percent      — фактическая комиссия, %
payout                  — сколько получит продавец за единицу
price / old_price       — цена и цена до скидки
total_discount_value    — размер скидки в рублях
total_discount_percent  — глубина скидки
currency_code, product_id, actions
```

Достаточно расширить тип и проекцию — **ноль дополнительных запросов к Ozon**, а дашборд
получает комиссию, payout и маржу (пока без себестоимости) по каждому заказу. Это самый
дешёвый способ получить 80 % финансовой ценности.

Осторожно: у `financial_data.products[].quantity` есть известный дефект — у части
FBO-заказов поле отсутствует или приходит как `"0\""`. Количество надо брать из
верхнеуровневого `products[].quantity`.

### 5.2 Честная критика текущих метрик

| Место | Проблема как финансового инструмента |
| --- | --- |
| `inventory.ts` — `inventoryValue` | Считает запас по **цене продажи**. Это не актив и не оборотный капитал, а «выручка, которая могла бы быть». Завышает капитал и делает GMROI невозможным. Нужны две оценки: в закупке (COGS) и в ценах продажи. |
| `dead` / `overstock` | Считаются **в штуках**. Не видно, сколько денег заморожено — то есть главного числа. |
| `outOfStock` | Только счётчик. Нет упущенной выручки и упущенной маржи, хотя `demandPerDay` уже посчитан. |
| `revenueConcentration` | ABC **по выручке**. Товар с 30 % выручки и 5 % маржи выглядит лидером. Нужен ABC по марже. |
| `stats.ts` — `netSum` | Вычитает только отменённые заказы. Комиссия, логистика, эквайринг не вычитаются вообще, поэтому «Net Sales» — это не net. |
| `compareWindows`, `dailyTrend` | Динамика по выручке. Экономисту нужна динамика по payout и марже. |
| Возвраты | Учитываются только `cancelled`. Возвраты и невыкупы — отдельный поток затрат (обратная логистика) — не видны. |
| Расходы кабинета | Отсутствуют. Хранение и реклама не попадают никуда, поэтому любая «маржа» будет завышена. |

### 5.4 Технические требования, вытекающие из API

- **Кешировать закрытые дни навсегда.** Обход `accrual/by-day` — это запрос на каждые
  сутки: 31 день = 31+ запросов. Но начисления за прошедший день больше не меняются,
  поэтому хранить их локально (IndexedDB) и догружать только последние 3–5 дней.
  Без этого экран будет медленным и упрётся в лимиты.
- **`turnover/stocks` — 1 запрос в минуту.** Не звать при каждом заходе;
  `refreshInterval` ≥ 5 минут, кеш в `localStorage` с TTL.
- **Финансовые отчёты асинхронны.** `/v1/report/*/create` возвращает код, потом
  `/v1/report/info` — статус, потом файл. Это фоновая задача, а не часть загрузки страницы.
- **Метрика свежести на каждый источник.** Не «запрос прошёл», а «когда последний раз
  реально приехали данные»: `max(operation_date)`, `max(created_at)` заказов,
  время последнего turnover. Если финансовые данные старше 3 дней при наличии доставленных
  заказов — тревога. Именно отсутствие такой метрики позволило одному продавцу **две
  недели считать прибыль на мёртвых данных** после отключения метода.
- **Пустой ответ ≠ ноль.** Технический пробел нельзя записывать как «начислений нет» и тем
  более показывать нулём. Это ровно тот класс ошибок, который мы уже починили в UI
  (скелетоны вместо нулей и плашка «показаны устаревшие данные») — теперь его нужно
  закрыть и на уровне данных.
- 429 уже обрабатывается с `Retry-After` (`src/lib/server/ozon.ts`), это переиспользуется.

### 6.3 Денежное тождество, проверенное на конкретном заказе

Разобрано живое отправление: карточка дала `цена 1499`, `комиссия −779,48`,
`payout 719,52`; начисления по нему — `POSTING 634,16` с услугами `логистика −78,00` и
`доставка −7,36`, плюс `ITEM −17,17` (эквайринг). Тогда:

```
719,52 − 634,16 = 85,36 = 78,00 + 7,36          (услуги внутри POSTING)
719,52 − 616,99 = 102,53 = 78,00 + 7,36 + 17,17 (плюс эквайринг из ITEM)
```

Отсюда два вывода, которые определяют формулировки в интерфейсе:

1. **`payout` в карточке заказа не включает логистику, обработку и эквайринг.** Это
   цена минус комиссия. Поэтому его нельзя называть «к перечислению» — раньше подпись
   была именно такой, и она завышала деньги примерно на стоимость логистики.
2. **`total_amount` начисления уже нетто**: услуги, перечисленные внутри начисления,
   из него уже вычтены. Поэтому строки удержаний — это атрибуция, а не слагаемые.

### 6.4 База, к которой считается комиссия, — не выручка

Это самая неприятная находка. Отношение суммы по карточкам к реализованной выручке из
отчёта по отдельным SKU гуляло от 0,54 до 2,64, а по кабинету в целом составило около
1,7. Причина не в ценах, а в том, что **сравниваются разные множества**: отчёт строится по
дате реализации, карточки — по дате создания заказа, поэтому заказ конца месяца попадает
в один источник и не попадает в другой. Из-за этого:

- ставку комиссии из карточек нельзя показывать как «долю, которую Ozon забирает от
  выручки»;
- суммы по конкретному SKU нельзя сверять между отчётом и карточками напрямую.

Исправлено в интерфейсе: показатель называется «Сумма по карточкам заказов», ставка
подписана как «к цене карточек», а рядом с деньгами прямо сказано, что это ещё не
поступление на счёт. Точная сверка «заказ против начисления» возможна через
**`/v1/finance/realization/posting`**: он отдаёт те же строки, но с `order.posting_number`,
то есть с ключом, по которому строка отчёта связывается с начислениями. Это следующий шаг
для этапа C.

### 6.5 Что осталось непроверенным

- Требование подписки для `ReviewAPI` — не проверялось, у кабинета её может не быть.
- `/v1/finance/balance` — форма не подтверждена.
- Что означает `seller_price_per_instance` в отчёте о реализации относительно `price` в
  карточке: в отчёте он примерно вдвое больше реализованной суммы, и поле `bonus` рядом
  сопоставимо с этой разницей, но связь не доказана.

## 7. Риски

- **Бета-методы меняют форму без предупреждения.** Весь финансовый слой и оборачиваемость
  живут в бета-группе. Отсюда: рекурсивный парсер вместо жёсткой схемы, метрики свежести,
  и тесты на разбор с фикстурами реальных ответов.
- **Один источник — не истина.** Payout из карточки заказа и payout из accrual могут
  расходиться (см. п. 6.2). Пока не сведены — показывать один и помечать происхождение.
- **Себестоимость быстро устаревает.** Нужна история COGS по датам, иначе маржа за прошлый
  период пересчитается задним числом при изменении закупочной цены.
- **Соблазн размазать расходы кабинета по заказам.** Практик прямо предупреждает: не надо,
  иначе цифра перестанет сходиться с кабинетом.
